## 1. 基础定义

### 1.1 用户 (User)

通过 **钱包共现图的连通分量 (Union-Find)** 聚合识别的实体。一个 User 包含一个或多个 `wallet_id`。

- 用户是所有下游分析的最小统计单位
- 同一 User 的资产在汇总前需去重(避免同一 token 在多钱包重复计数)

### 1.2 活跃度分层

基于用户最近一次打开 App 的时间戳:

| 层级 | 条件 | 颜色标识 |
|------|------|---------|
| Active | ≤ 7 天 | 🟢 |
| Recent | 7 – 30 天 | 🟡 |
| Dormant | 30 – 365 天 | 🔵 |
| Silent | > 365 天 | ⚪ |

用于 §4 分群时的次级切片,并非分群主维度。

### 1.3 资产持仓三态

对 `(User u, Token A, Chain X)` 三元组,持仓分三态:

| 状态 | 符号 | 数据源 | 含义 |
|------|------|-------|------|
| 钱包裸持仓 | `W(u,a,x)` | OneKey 钱包余额 | 未参与任何 DeFi |
| 外部 DeFi | `E(u,a,x)` | debank portfolio | 外部协议 yield/supply/deposit 类仓位 |
| OneKey DeFi | `O(u,a,x)` | OneKey DeFi 内部 | 通过 OneKey 存入的 DeFi 仓位 |

派生量:

- **总持仓**: `T(u,a,x) = W + E + O`
- **DeFi 持仓**: `D(u,a,x) = E + O`

**聚合规则**: 所有跨用户、跨 token 求和必须按 **USD 本位**(避免 token decimal 差异)。公式里写 `Σ` 时默认是 USD 金额。

### 1.4 覆盖范围

```
Covered(A, X) = 1 ⇔ token A on chain X ∈ OneKey DeFi Earn 支持清单
```

覆盖内 token 才参与 §2 的核心指标计算,覆盖外 token 走 §3 的机会识别。

### 1.5 Snapshot 对齐

同一 User 的 `W` / `E` / `O` 三类 snapshot 时间差 **≤ 72 小时**,超过则标记 `stale`,不进入指标聚合。

## 2. 核心指标

以下公式中 `Σ` 表示对目标用户集合的求和;若未特别说明,目标集合 = 该 token 有持仓的全体 User。

### 2.1 OneKey 份额 — Share

**问**: token A on chain X 的 OneKey 用户总持仓中,OneKey DeFi 吃到多少?

```
Share(A, X) = ΣO / (ΣW + ΣE + ΣO) = ΣO / ΣT
```

### 2.2 覆盖基线 — DeFiRate

**问**: 市场上这个 token 天然的 DeFi 倾向有多强?

```
DeFiRate(A, X) = (ΣE + ΣO) / ΣT = ΣD / ΣT
```

**Share 与 DeFiRate 的 gap** = OneKey 在该 token 上的覆盖缺口(见 §6.1)。

### 2.3 转化效率 — Efficiency

**问**: 在已经有 DeFi 意图的用户里,OneKey 抓到多少?

```
Efficiency(A, X) = ΣO / (ΣE + ΣO) = ΣO / ΣD
```

### 2.4 效率双基线

#### 基线 A — 市场均值基线

全盘 OneKey DeFi 的平均效率,作为单 token 的整体参照:

```
EffBaseline_market = Σ_{全(A,X)} ΣO / Σ_{全(A,X)} ΣD
```

单 token 的 `Efficiency(A,X)` 与此基线对比,看该 token 是"溢价吸引"还是"折价遇冷"。

#### 基线 B — 同桶均值基线

按资产价值桶 i 聚合,看同桶用户对该 token 的效率 vs 桶内均值:

```
EffBaseline_bucket(i) = Σ_{u ∈ bucket_i} O(u,*,*) / Σ_{u ∈ bucket_i} D(u,*,*)
```

两基线并用: A 告诉你 "这个 token 是否异常", B 告诉你 "这个价值段的用户是否异常"。

### 2.5 转化潜力(双池)

不做加权,直接展示两个绝对值池子:

| 指标 | 公式 (USD) | 策略用途 |
|------|------------|---------|
| **存量 DeFi 抢占池** | `ΣE(A,X) × price(A,X)` | 从外部 DeFi 迁移过来的天花板 → 竞品抢占赛道 |
| **钱包激活池** | `ΣW(A,X) × price(A,X)` | 钱包闲置转化的天花板 → 钱包激活赛道 |

分别排 Top-N。等累积 2–3 个月真实转化数据后,再回过头拟合加权系数 `k_defi`、`k_wallet`。

## 3. 覆盖外 Token 分析

对 `Covered(A,X) = 0` 的 token,`O = 0`,只剩 `W / E`。用于回答: "下一个要接入 Earn 的 token 是哪个?"

### 3.1 机会评分

```
OpportunityScore(A, X) = (ΣE + α × ΣW) × price(A, X)     (α 初期建议 0.2)
DeFiWillingness(A, X)  = ΣE / (ΣW + ΣE)
```

- `OpportunityScore` 倒序 → Earn 扩品优先级清单
- `DeFiWillingness` → 接入后可期的效率上限(>50% 的 token 说明用户自发 DeFi 倾向强)

## 4. 用户画像分群 × 资产价值桶

### 4.1 分群二维

#### 维度 1 — DeFi 使用状态 (3 类,互斥)

| 分群 | 判定条件 |
|------|---------|
| `NonDeFi` | 所有 (A,X) 都满足 E = 0 且 O = 0 |
| `ExtDeFi` | ∃ (A,X) 使 E > 0, 且 所有 (A,X) 满足 O = 0 |
| `OneKeyDeFi` | ∃ (A,X) 使 O > 0 (允许同时有 E) |

#### 维度 2 — 用户总资产价值桶 (5 档,固定阈值)

| 桶 | 范围 (USD) |
|----|-----------|
| 微型 | < $100 |
| 小型 | $100 – $1k |
| 中型 | $1k – $10k |
| 大型 | $10k – $100k |
| 巨鲸 | > $100k |

两维交叉 = **15 个画像格子**。

### 4.2 每格输出内容

对每个 `(segment × bucket)` 格子:

1. 用户数、资产总量 (描述性)
2. Top-N token 组成(数量、USD、链分布)
3. 链偏好分布
4. (仅 `ExtDeFi` / `OneKeyDeFi`) 协议类型分布: yield / lending / LST / staking / RWA / 其他
5. 活跃度分层分布

### 4.3 关键交叉对比

| 目标格子 | 诊断问题 | 产出清单 |
|---------|---------|---------|
| `NonDeFi` × 大 / 巨鲸 | 钱包里躺的 token 哪些已在 Earn 覆盖? | 钱包激活目标清单 |
| `ExtDeFi` × 中 / 大 | 钱放在哪些竞品?协议类型是什么? | 竞品抢占 + 产品缺口清单 |
| `OneKeyDeFi` 且 E > 0 × 大 | 外部那部分为什么没搬过来(链 / 协议 / APY)? | 存量用户深挖清单 |

## 5. 高 ROI 目标用户识别

### 5.1 单用户双维 ROI

```
ROI_DeFi(u)   = Σ_{(A,X) ∈ coverage} E(u,A,X) × price(A,X)
ROI_Wallet(u) = Σ_{(A,X) ∈ coverage} W(u,A,X) × price(A,X)
```

**只计入覆盖内 token**,因为覆盖外的转化概率为 0。

### 5.2 双榜排序

- **ROI_DeFi Top-N** → 竞品抢占目标清单
- **ROI_Wallet Top-N** → 钱包激活目标清单
- **两榜交集** → 最高价值目标,优先攻

### 5.3 格子级策略映射

| 分群 × 桶 | 典型策略 |
|----------|---------|
| `NonDeFi` × 大 / 巨鲸 | 保本型稳定币 Earn 引导 + 教育("X 万 USDC 一年少赚 Y") |
| `ExtDeFi` × 中 / 大 | 对标协议 APY 对比页 + 迁移 gas 补贴 |
| `OneKeyDeFi ∩ ExtDeFi` × 大 | 缺失链/协议作为 roadmap 输入,解决"为什么没搬过来" |
| `NonDeFi` × 微 / 小 | 低门槛入门产品 + 社区教育,ROI 权重低,长线培育 |

## 7. 实施路径

### Phase 1 — MVP (2–3 天)

不等全量 ETL,用小样本验证方案闭环:

1. 选 5 个代表 token: `USDC` / `USDT` / `ETH` / `WBTC` / `stETH`
2. 选 2 条主流链: `Ethereum` / `Arbitrum`
3. 跑最近 7 天 snapshot,产出:
   - §2 的 5 组指标
   - §4 的 15 个格子描述
   - §6.1 / §6.3 / §6.5 三张核心图
4. 内部评审: schema / 分群逻辑 / 图表是否符合决策需求

### Phase 2 — 全量扩展 (1–2 周)

- 扩到全量 token × 全链
- 补齐 §6.2 / §6.4 / §6.7 / §6.8 的图
- 建立每周定时跑批

### Phase 3 — 运营闭环 (持续)

- §6.5 ROI 双榜每周输出给运营
- 跟踪 Top-N 清单的实际转化率
- 根据反馈拟合 §2.5 的 `k_defi` / `k_wallet` 权重(Phase 2 先只用绝对值,Phase 3 开始加权)
- §6.6 桶迁移矩阵每月跑一次,看是否需要调整 §4.1 的阈值

## 8. 附录

### 8.1 核心字段清单

#### user 表
- `user_id` (Union-Find 主键)
- `wallet_ids[]`
- `last_active_at`
- `activity_tier` ∈ {Active, Recent, Dormant, Silent}

#### holdings_snapshot 宽表 (User × Token × Chain × 日期)
- `user_id`, `token_symbol`, `chain_id`, `snapshot_date`
- `w_amount`, `w_usd` (钱包)
- `e_amount`, `e_usd` (外部 DeFi)
- `o_amount`, `o_usd` (OneKey DeFi)
- `protocol_name`, `protocol_type` (外部 DeFi 细分,可 NULL)
- `snapshot_time_spread_hours` (三源时间差,用于 stale 过滤)

#### user_bucket 表 (User × 日期)
- `user_id`, `snapshot_date`
- `total_usd`
- `asset_bucket` ∈ {微型, 小型, 中型, 大型, 巨鲸}
- `defi_segment` ∈ {NonDeFi, ExtDeFi, OneKeyDeFi}

#### coverage 表
- `token_symbol`, `chain_id`, `is_covered`

### 8.2 宽表概念模型

