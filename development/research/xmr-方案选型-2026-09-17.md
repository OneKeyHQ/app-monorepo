# XMR 接入方案选型：LWS vs 本地扫链

2026-09-17

## 推荐结论，但是也要考虑成本

**选 LWS（轻钱包服务器），不做本地扫链。**

理由：**Monero 的扫链负担量级上是 Zcash 的 10 倍，而 Zcash 我们已经在手机上跑到接近极限。**

代价：**view key 要交给服务器**，用三条措施压到最小（见 §5）。

---

## 1. LWS 有几种


| 形态          | view key 归谁 | 现状           |
| ----------- | ----------- | ------------ |
| A 第三方公共 LWS | 陌生第三方       | **不存在**      |
| B 厂商自建自运营   | 厂商          | 可行（Edge）     |
| C 用户自填 / 自建 | 用户自己        | 可行（Skylight） |


A 是空的：MyMonero 于 2026-01-06 关服、02-06 销毁数据，理由是「view key 型轻钱包与 Monero 隐私演进方向冲突」；**且不存在任何公共 LWS 目录**，连 Skylight 也不预置服务器。

**我们可以选 B + C**：自建一台作默认，允许用户一键换成自己的。

## 2. 扫链有几种


| 客户端库                                      | 形态           | 谁在用                             |
| ----------------------------------------- | ------------ | ------------------------------- |
| A 原生 `wallet2`（`monero_c` / Monerujo JNI） | 各平台原生库       | Cake、Monerujo、Stack、Unstoppable |
| B `wallet2` 编 WASM（`monero-ts`）           | WASM，5.93 MB | Haveno                          |
| C Rust 独立实现（`monero-oxide`）               | WASM，226 KB  | **无产品先例**                       |


正交维度：自建全节点（≈280 GB）还是连远程节点，主流是后者。

## 3. 两类的差别


|          | LWS       | 扫链            |
| -------- | --------- | ------------- |
| 谁扫链      | 服务器       | **用户设备**      |
| view key | **交给服务器** | 不出设备          |
| 客户端流量    | 极小        | **13.5 MB/天** |
| 手机后台同步   | 不需要       | **不能**，只能前台   |
| 四端是否各付一次 | 否，共享服务端状态 | **是，每端各扫一遍**  |
| 插件端      | 能         | 理论能，**无先例**   |
| 需要后台运维   | **有**     | 无             |


## 4. 实现差异

两条路的**密钥与交易构造完全相同**：都用 `monero-oxide` 编 WASM，实测 **226 KB**。差异只在数据来源与本地状态：


| 模块          | LWS             | 扫链                       |
| ----------- | --------------- | ------------------------ |
| 链数据获取       | **自写 REST 客户端** | 上游全包（含二进制 RPC 与 epee 解析） |
| 诱饵（环签名）     | **自写接入**        | 上游全包                     |
| 区块扫描        | 不需要             | 上游 `Scanner` 现成          |
| **本地钱包数据库** | **不需要**         | **必须自建**                 |
| 移动端后台       | 不需要             | **需额外解决，iOS 无解**         |


> 论库支持度，扫链方案其实**更完整**。它的成本不在库，在下一节。

## 5. 为什么选 LWS

**扫链负担量级是 Zcash 的 10 倍。** 归一化到「每笔链上交易」（与链上活跃度无关）：


| 指标         | Monero | Zcash | 倍数         |
| ---------- | ------: | -----: | ----------: |
| 每笔交易的扫描带宽  | 504 B  | 72 B  | **7.0×**   |
| 每笔交易的试解密次数 | 2.09   | 0.62  | **3.4×**   |
| 单次解密的密码学成本 | —      | —     | **≈ 1.0×** |


按当前活跃度折算绝对量：**13.5 MB/天 vs 1.04 MB/天，13 倍**（含活动量因素会波动）。**"约 10 倍"是量级判断，区间 7–13。**

差距来自两条协议层设计，工程优化改不掉：**Monero 没有透明交易池**（100% 交易须试解密，Zcash 只处理屏蔽部分）、**没有精简区块协议**（每候选 241 B vs 116 B）。

> 防误读：这个倍数说的是**数据量**，不是"XMR 加密更难"。逐个候选看两边密码学成本相当，Zcash 因多一层承诺树反而略重。

**而 Zcash 在手机上已接近极限。** 2026-09-16 安卓旗舰机（Android 16 / arm64 / 15.4 GB RAM）实测 Zcash：扫描 52.4 块/秒（1 账户）／18.3（4 账户），WASM 内存 295–390 MB，**首次扫描 5 账户约 1.7 小时**（慢 10 倍的机器约 17 小时），**且首扫必须前台**——应用切后台，WebView 定时器与网络即挂起。**这是 Zcash 的数字，Monero 再乘 10 倍量级。**

**三个叠加因素：**

1. **四端各扫一遍** —— 钱包缓存是解密后的数据，不能跨设备同步。桌面+手机+插件 = 三份完整扫描。LWS 下服务端按账户存进度，**四端共享只等一次**。
2. **移动端只能前台扫** —— 安卓或许能用前台服务绕开（未验证），**iOS 无解**，Cake Wallet 官方也承认 iOS 必须保持应用打开。
3. **Monero 助记词不带创建高度** —— Zcash 有 birthday，Monero 没有，导入旧钱包只能往更早扫。回补到 2022 年同一窗口：**Monero ≈ 21 GB，Zcash ≈ 1.6 GB**。

**代价与对策。** monero-lws 自带审计（Monero 核心贡献者所作）划清边界：**资金安全**（spend key 永不上传），**隐私不安全**——持有服务器者可确定用户「收到的全部输出，多数情况下还包括花费的输出，以及金额」。且 view key 在协议层**不可轮换**，泄露一次即该钱包全部收款历史被追溯解密。


| 对策                          | 状态        |
| --------------------------- | --------- |
| **客户端可切换服务器**（默认连我方，一键改为自建） | 硬性要求      |
| **诱饵不由服务器选**（客户端自取输出分布本地选）  | **已实测跑通** |
| **广播路径与查询分离**               | 设计要求      |


另有安全清单（数据加密、不记 IP、不存 view key 与账号映射、onion 端点），随部署同批上线。

## 6. 服务端

**只有 `vtnerd/monero-lws` 一个能选**（openmonero 停 2022-07，MyMonero 的停 2018/2021）。**没有选择余地是本路线的固有风险。**


| 支持可靠                                       | 风险                                           |
| ------------------------------------------ | -------------------------------------------- |
| **8 天前发 v1.0.0**（2026-09-09），已迭代到 v1.0.2   | **bus factor = 1**，86% 提交出自一人                |
| CI 双平台 build + `ctest`，单测约 110 KB（扫描器覆盖最重） | 无第二实现可退                                      |
| CCS 持续全职资助，2020 年至今未断                      | 2022 年那份非正式审计的威胁模型是"用户自建自用"，**不覆盖厂商为大量用户托管** |
| 第二贡献者是 Monero 核心开发                         | FCMP++ 适配仍在分支                                |


**四条开着的 issue 直接命中自建场景**：`#183` 大量账户重扫时 LMDB 写吞吐受限、`#241` 重扫时 `MDB_MAP_FULL`、`#156` 自转账余额算错（已开 18 个月）、`#261` 有人问单实例账户承载量而**上游无答案**。

**成本模型**：LWS **按账户扫描**，CPU 随「账户数 × 各自回补块数」增长。真正的成本驱动不是用户总数，而是**有多少用户导入了旧钱包、回补多深**——新建钱包几乎零成本。

**两条影响用户承诺的限制**：**账户无法删除**（只能停用，冲击"删钱包即删数据"的隐私政策）、**mempool 不经 wallet API**（0-conf 只能靠 webhook）。

**采纳前置条件**：① 自行做容量压测（上游无容量模型）；② 锁版本 + 自建构建，升级前备份（**DB 迁移不可回滚**）；③ 准备上游断供预案。

> 部署细节（组件、镜像 tag、必改的默认配置项）见长文 §3.4。

## 7. V4 用的是什么

**V4 就是 LWS 方案。** `packages/engine/src/vaults/impl/xmr/ClientXmr.ts`（`b94a72b0f2`，2023-03-29）：

```ts
import LWSClient from '@mymonero/mymonero-lws-client';
this.wallet.login(privateViewKey, address, true);
```

**私有 view key 直接发给服务器。** 双端点（monerod 只取块高与手续费 / LWS 取钱包数据）；加密栈是 `mymonero-core` WASM（2.46 MB）；**无硬件钱包支持**（`KeyringHardware.ts` 是空类）。

**为什么不能继续用：**

1. **加密库上游已死** —— `mymonero-core-cpp` 最后提交 2022-10-20，公司解散。后果不是年久失修而是硬性失效：**FCMP++ 硬分叉当天交易会被网络拒绝，且无人会修**。
2. **体积差一个数量级** —— 2,456,152 B vs monero-oxide 225,626 B，**10.9 倍**。
3. **基础设施已不在** —— V4 的 RPC 节点 `https://node.onekey.so/xmr` **域名已无法解析**。

**查不到的一项**：V4 的 LWS 服务器地址无法确定。`scanURL` 在 `@onekeyfe/network-list` 全部采样版本（2023-02→05）均为 null，远端配置源域名也已失效，**只能问后端**。

> **V4 的壳是对的，芯要换。** 不是架构选错了，是里面那块加密库死了。
