# XMR 接入方案汇报

2026-09-17

## 一、结论

经过一轮反方论证，我原来推荐的「自建服务器代扫」不再是首选建议。现在这是一个需要产品和管理层拍板的多选题，工程侧不应该替它做决定。

真正该先回答的不是「用哪种扫链方案」，而是两个更靠前的问题：第一，要不要做 XMR；第二，如果做，是不是应该做硬件签名而不是软件钱包。扫链方案的选择排在这两个之后。

## 二、XMR 接入的两大类方案

第一类是轻钱包服务器，业内简称 LWS，就是让服务器替用户扫链。用户要把自己的 view key 交给服务器，服务器用它找出属于这个用户的交易，再把结果推回客户端。按谁运营这台服务器，又分三种：第三方运营的公共服务器、钱包厂商自己运营、用户自己搭建。

第二类是本地扫链，密钥不出设备，客户端自己从节点拉区块、自己解密。按客户端用什么库实现，分三种：用 Monero 官方的原生库（Cake、Monerujo、Stack、Unstoppable 都是这条），把官方库编译成 WebAssembly（Haveno 用的 monero-ts 属于这条），或者用 Rust 重写的独立实现（monero-oxide 这条）。

另外还有一个和上面正交的维度：是自己跑一个全节点（磁盘约 280 GB），还是连别人的远程节点。市面主流是后者。

## 三、公共 LWS 服务器实际上不存在

这一点需要单独说明，因为它排除了一个看起来存在的选项。

运营了十二年的 MyMonero 已于今年 1 月 6 日关服、2 月 6 日销毁全部数据，官方给的理由是「需要 view key 的轻钱包与 Monero 的隐私演进方向冲突」。此外全网不存在任何公共 LWS 服务器目录。monero-lws 项目里有人在五月开了个 issue 问「有没有一份公共维护的 LWS 端点列表」，四个月无人回复，提问者自己起的列表只有一条，而那一条我测过，返回 401 需要授权，并不对外开放。

所以「让用户自己填一个服务器地址」听起来像折中方案，实际上更糟。用户能填到的基本都是来路不明的服务器，而恶意服务器不只是能看到你的全部收款历史——它还负责给你挑选环签名的诱饵，可以永久破坏你链上交易的匿名性，而且这种破坏是公开的、换服务器也救不回来。所以这不是把选择权还给用户，是把风险甩给用户。

## 四、本地扫链在四个端上的实际情况

这是我之前汇报得不完整的地方。我一直只讲手机端，但四个端的约束完全不同。

桌面端最宽松。运行在 Electron 里，App 开着就一直扫，操作系统不会挂起；存储没有配额限制；CPU 是完整的桌面多核。桌面还是唯一一个能顺便跑本地全节点的端。每天十来兆的流量在桌面上不算事。

插件端也可以。我们的插件已经常驻一个 offscreen 文档，本来是给 service worker 保活用的，它有完整的网络、Worker 和 WebAssembly 能力，Zcash 已经在上面跑通。存储方面我们的 manifest 已经声明了 unlimitedStorage，钱包数据库放得下。它的限制只有两条：只在浏览器开着时推进；用户清除站点数据后钱包库会丢失，可以用 view key 重建，但要重新全量扫一遍。

Web 端勉强。标签页必须开着，而且网页环境拿不到 unlimitedStorage 权限，只能请求持久化存储而浏览器不保证批准，数据有被回收的风险。

只有手机端真的不行。我们的运行时跑在 WebView 里，App 一进后台，定时器和网络就被挂起。安卓也许能用前台服务绕过去，但我们没有验证过；iOS 根本没有等价的办法，Cake Wallet 官方也承认 iOS 用户必须保持 App 打开。

补充一点：分端做不同策略这件事我们已经在做了。现有代码里桌面的回填延迟是单独一档，手机端还有蜂窝流量门控，回填需要用户同意才走移动数据。

## 五、五个可选方案

第一，全端都用 LWS。view key 交给服务器，四端体验一致，我们要承担运维。

第二，全端都本地扫。密钥安全、零运维，但手机端体验差，首次同步要用户盯着屏幕等。

第三，桌面和插件本地扫，手机端不提供 XMR。密钥完全安全、零运维，代价是手机上没有这个功能。Trezor 选的就是这个方向，而且更极端——他们连插件都不做，只做桌面。

第四，桌面和插件本地扫，手机端用 LWS。这看起来是折中，实际是陷阱。只要手机端用了 LWS，view key 就已经交出去了，桌面和插件再本地扫也救不回来。等于同时承担服务器责任和客户端扫描工作量，拿到最差的组合。建议直接排除。

第五，不做。

## 六、V4 用的是什么，能不能继续用

V4 用的就是 LWS 方案，这一点有代码为证。V4 的客户端代码里直接引入了 MyMonero 的 LWS 客户端库，调用 login 时把用户的私有 view key 连同地址一起发给服务器。它是双端点设计：一个 monerod 只用来取块高和手续费，钱包数据全部走 LWS。加密栈是 MyMonero 的 WebAssembly 模块，2.46 MB。V4 没有硬件钱包支持，那个 KeyringHardware 文件全文只有一行空类。

现在不能直接复用，有三个原因。

第一，加密库的上游已经死了。MyMonero 的 C++ 核心最后一次提交是 2022 年 10 月，公司已解散。它的 29 个 fork 全部停在 2019 到 2022 年之间，或者是山寨币自己的分叉，没有任何人在为 Monero 的下一次硬分叉做适配。硬分叉之后这个库仍然能收款和查余额，但构造不出合法的花费交易，而且不会有人来修。需要说明的是，这个硬分叉目前没有官方时间表，里程碑 39 项里关了 27 项，所以这是「迟早必须换」，不构成「现在不能上」的阻塞。

第二，体积差一个数量级。V4 那个模块 2.46 MB，而我实测编译 monero-oxide 只有 226 KB，差 10.9 倍。

第三，V4 用的服务器已经不在了。它的 monerod 节点域名现在 DNS 都不解析。至于 LWS 服务器的地址，我查不到——那个字段在网络配置里全部版本都是空的，远端配置源的域名也已失效，只能问后端。

还有一点需要纠正我之前的说法。我说过「V4 的壳是对的，芯要换」，这句话低估了工作量。V4 的 Vault 依赖的是 v4 那套 engine 架构，而 v5 现在的 vault 契约完全不同。Vault 和 Keyring 无论换不换加密库都要重写。准确的说法是：架构方向可以沿用，代码基本要重写。

## 七、如果自建服务器，技术选型是否可靠

服务端软件没有选择余地，全行业只有 monero-lws 一个还在维护的实现。另外两个，openmonero 停在 2022 年 7 月，MyMonero 自己的停在 2018 和 2021 年。

支持它可靠的证据是：八天前刚发布 1.0.0 版本，一周内已迭代到 1.0.2；CI 在两个平台上编译并跑测试；单元测试大约 110 KB，其中扫描器这个正确性最关键的部分覆盖最重；由 Monero 社区众筹持续全职资助，2020 年至今没断过；第二贡献者是 Monero 核心开发者。

但风险也是实打实的，而且这一轮查到了几条之前不知道的。项目 238 次提交里 208 次出自同一人。仓库没有 SECURITY.md，没有漏洞披露流程，却要托管全量 view key。更要紧的是作者本人在 issue 里的原话：关于容量，他说「我没做过测试来给出估计」；关于多机横向扩容，他说「我认为它可以用于生产，但我不知道有任何人实际部署过这个功能」；而且他明确指出多机扩容的主要限制是「子地址无法与该功能一起工作」——而子地址是 Monero 收款的必需品，虽然有人提了变通办法但更耗 CPU。

另外有两条限制会直接影响我们对用户的承诺。一是账户删不掉，官方文档原话是「目前不支持删除账户」，只能停用，这和「删除钱包即删除服务端数据」的说法冲突。二是有一个已知缺陷，交易里的加密 payment ID 在一笔交易中只解密一次然后跨所有注册账户共享——这是只有多租户场景才会触发的问题，单用户自建碰不到，恰恰是我们这种形态才会碰到。

成本模型上还有一个容易估错的地方：LWS 是按账户扫描的，不是扫一遍供所有人共享。CPU 成本随「账户数乘以各自需要回补的块数」增长。所以真正的成本驱动不是有多少用户，而是有多少用户导入了旧钱包、回补得多深。新建钱包几乎零成本，因为起始高度就是链尖。

## 八、一个新情报：竞品和上游都在往另一个方向走

Trezor 已经把 Monero 硬件签名的 SDK 发布了正式版，里面有四个真实的 API 方法：取地址、取观察密钥、密钥镜像同步、签名交易。而我们的 SDK 里只有协议定义，一个 API 方法都没有。

他们正在做的完整钱包方案，架构写得很清楚：本地节点、客户端用 view key 自己扫、Trezor 签名。也就是说 view key 根本不出用户的机器——和我原来推荐的方向正好相反。不过要说明两点：这个方案还是草稿状态，两个多月没动了；而且它只做桌面，绕开了手机端，没有解决手机的问题。

另一家竞品 Keystone 走得更远，他们的硬件钱包固件里已经有 Monero 应用，用的正是 monero-oxide 那条 Rust 库，跑在嵌入式环境里，固件两天前还在更新。

这两件事对我们有两个含义。一是「monero-oxide 没有产品先例」这个说法要改，它不但有先例，还是跑在比我们苛刻得多的嵌入式环境里。二是我们自己的固件其实也继承了 Monero 实现，缺的只是 Trezor 已经做完的那层 SDK——如果做硬件签名，我们会是第一个把 XMR 硬件签名放进自家四端 App 的厂商。

## 九、这一轮反方论证推翻了什么

我组织了三个独立的反方论证，分别攻击「应该选 LWS」「本地扫链不可行」「V4 必须换」这三个结论。三个的结论都是「需要重大修正」。

第一，我原来的主论据「Monero 的扫链负担是 Zcash 的 10 倍」撑不住。那是一个带宽比值，被我错误地乘到了 Zcash 那个 CPU 受限的时间上。用我们自己的实测数据反推，Zcash 每块的固定开销约 7.2 毫秒、每个账户的试解密约 11.9 毫秒，而那 7.2 毫秒里很大一部分是承诺树维护——Monero 没有承诺树，这部分不转移。真实的 CPU 差距大约是 1 到 3 倍，不是 10 倍。汇报时不要引用这个数字。

第二，我写过「Monero 助记词不带创建高度」，这是错的。Polyseed 规范明确把钱包创建日期编进了助记词，2021 年 11 月起可用。而 Zcash 的创建高度反倒不在助记词里。这条不对称基本不存在。

第三，「四个端各扫一遍」这个理由不成立，因为同一个乘数对 Zcash 完全适用，而 Zcash 我们已经上了。同一条理由不能只用来否决 XMR。

第四，我们自己的仓库给出了一个不该忽略的信号：XMR 的代码 2023 年 10 月就引入了，至今三年，16 次提交逐条看全是全仓范围的 lint、TypeScript 升级、改名这类扫射，没有一次是 XMR 的功能推进，也没有人要求做完。

## 十、待决事项

需要管理层回答的：要不要做 XMR，收益是什么。这个问题从头到尾没有人评估过，我们的研究全部在回答「怎么做」。如果做，是做软件钱包还是优先做硬件签名。

需要法务回答的：XMR 的合规口径。这一条可能直接否决整个项目。需要说明的是，反方论证里提到的欧盟法规条文和几个司法案例，我这边无法独立核实——这一轮网络搜索工具全程不可用——所以那些内容不要带进决策会议，必须由法务自己查证。

需要工程继续做的：如果选自建服务器，必须先自己做容量压测，因为上游没有容量模型，而且横向扩容没有任何人部署过；交易的最终装配和广播还没验证过，需要一个有资金的测试钱包，自建一个测试网实例就能完成。

## 十一、已经验证过的事实

加密库 monero-oxide 能编译到 WebAssembly，产物 226 KB，包含地址解析、扫描、交易构造、签名和证明。编译耗时 21 秒，没有打任何补丁。

诱饵数据源可以由客户端自己掌握，不必依赖服务器。我写了一个实现对主网实跑，输出分布通过了上游自带的校验，取回的 16 个环成员全部合法。这一条很重要，因为它掐掉了恶意服务器最狠的那个能力。

四个端的运行时载体已经在 Zcash 上建成并验证，可以直接复用。
