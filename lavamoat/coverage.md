Each corresponding `lavamoat:policy:<target>` command discovers permissions. Discovery does not approve capabilities. Overrides are manually reviewed inputs and cannot be written by the generated-policy update workflow. The four Electron service entries use separate policies so generating one cannot replace another's permissions. A first-party-only enum entry can legitimately produce an empty policy.

The three extension outputs must be combined with `yarn workspace @onekeyhq/ext lavamoat:finalize`. It rejects conflicting staged files and runs the existing extension output checks. The aggregate protected build already includes this step. The page compiler covers popup, expand-tab, side-panel, standalone-window, content-script iframe, passkey, and offscreen documents. Its entry and lazy scripts use SRI against the final bytes, including the untouched SES prelude and existing remote-code removals. Background and content-script entries embed one raw SES runtime in their fixed manifest filenames.

## Isolation boundaries

Web and the Desktop application UI/background execute in one JS runtime. Electron main, each preload world, and service processes are separate runtimes; a renderer result cannot prove their state. Native addons and declared external SDKs are policy-controlled host capabilities, not recursively sandboxed package graphs.

The blockie-avatar Web Worker and the Web service worker are separate heaps outside the application package policies. The [service worker](../apps/web/src/service-worker.js) and its Workbox dependencies retain authority over app caches and controlled requests; its existing asset-integrity and update checks remain required. Protected page startup does not prove that either worker is hardened.

Mobile main/background execute independently in separate Hermes heaps. The same native process can share MMKV, DB/file handles, and module singletons. Each heap needs its own hardening and asynchronous-delivery checks, and neither runtime's readiness proves the other's. Native-vs-JS compatibility remains independent of version-locked main/background bundles.

React Native libraries can create additional worklet Hermes runtimes outside those two entry points. This integration does not install lockdown in those runtimes. Worklet runtimes and native modules remain trusted dependencies; main/background results do not establish their protection.

MV3 extension pages, background, offscreen, and content-script worlds do not share JS heaps. LavaMoat supplies a virtual `window` alias even in a worker compartment, so shared platform detection checks for a DOM Document before classifying a browser page. A real MV3 regression verifies worker, page, and isolated-content roles with the actual detection module. Content-script protection must not freeze the DApp's MAIN-world intrinsics. The existing injected provider is copied unchanged into the host page and remains a separately reviewed SDK boundary; it is not included in the extension compartments. Existing CSP and host permissions remain enforced during tests.

The official RN adapter uses `unsafe-eval` for Hermes compatibility and provides intrinsic integrity, not per-package capability isolation. The official Node runner covers the original CLI esbuild entry and dependencies discovered from that source. Its esbuild native child process intentionally retains build authority. It does not protect arbitrary repository scripts, Jest, signing infrastructure, or every release task.

Native authentication and hardware remain separate acceptance.        |
| CLI artifact smoke                | Production CLI entry, offline schema/commands, frozen intrinsics and absence of keyring loads                                                                       | Does not establish signed standalone installers, keyring operations or signing.                                                        |

Runtime reports must record the exact artifact hash or native/session/vendor identity, collected errors, and any controlled host responses. A test fails on uncaught errors, unhandled rejections, relevant asset failures, or missing runtime identity. Do not clear logs, disable CSP, or downgrade SES to obtain acceptance.

## Outstanding rollout constraints

The protected web-embed runtime contains untouched upstream SES 1.15.0. Its optional chaining and nullish syntax cannot parse on the existing Chromium 67 minimum. The application compatibility gate still rejects it. The [upstream webpack security guidance](https://lavamoat.github.io/guides/webpack/#security) requires loading SES without bundling or transforming it. Transpiling SES or excluding its bytes from the compatibility gate would invalidate the intended acceptance; the supported-engine decision remains unresolved.

Expanded real-WASM tests exposed Kaspa transaction-construction failures that earlier deserialization checks did not exercise. The SDK dynamically reads `crypto.getRandomValues`, creates three fixed function bodies through `Function`, and dynamically reads `location.protocol` to recognize an extension realm. Missing the last permission makes a second offscreen transaction wait indefinitely for an animation frame.

The integration now grants only the SDK browser RNG method in four browser policies and the read-only protocol property in extension pages. A loader verifies the pinned package, generated source, embedded and binary WASM hashes before replacing the three exact non-crypto function bodies with static functions inside the existing package compartment. Unknown bodies and receivers fail closed; the ordinary-browser scheduling path requires an existing callable animation-frame API and does not install a global fallback. Extension pages additionally load the same verified binary from a private packaged URL, retaining CSP and asset-access restrictions. Real MV3 fixtures passed two consecutive unsigned transactions for both byte-loading paths in actual offscreen documents. Current protected Web, Desktop, extension, CLI, iOS, and Android artifacts have separate bounded build or runtime evidence recorded above; these checks do not establish every chain operation or end-user flow.

Full application and native Release acceptance is still being completed. The CLI normal build emits its protected artifact at the existing `dist/cli.js` publishing path; `build:unprotected` is the explicit rollback command, and its five offline artifact checks passed with frozen intrinsics and no keyring loads. Web, Desktop, extension, and mobile production scripts now select protected builds in this branch, with the bounded artifact and runtime results recorded above. Desktop OTA updates only the renderer; the six Node/Electron entries require a complete binary release. The protected WebEmbed artifact still fails the unchanged Chromium 67 gate with 27 SES syntax violations and remains `releaseEligible: false`; wallet import/creation on the current Android candidate, signing, hardware, OTA rollback, notifications, and other application flows remain separate acceptance work. Final rollout must be based on exact protected artifacts, with explicit rollback commands and per-target evidence recorded here or in the linked mobile record.
