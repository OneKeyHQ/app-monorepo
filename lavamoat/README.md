# LavaMoat integration

This repository separates three supply-chain defenses: dependency installation control, JavaScript intrinsic hardening, and runtime package permissions. They have different coverage and rollout controls.

Tracking: [OK-56354 — supply-chain defense comparison](https://onekeyhq.atlassian.net/browse/OK-56354) and [OK-56774 — mobile lockdown integration](https://onekeyhq.atlassian.net/browse/OK-56774). Implementation: [PR #12155](https://github.com/OneKeyHQ/app-monorepo/pull/12155).

## Coverage

| Layer                                                          | Current implementation                                                                                       | Activation and limits                                                                                                                                                                                                                          |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dependency installation                                        | Native Yarn 4 lifecycle control, an explicit source/script approval inventory, and Git dependency validation | Enforced by repository Yarn configuration. Approved build scripts still execute with the install process's privileges. See [installation policy](supply-chain/README.md).                                                                      |
| Web application                                                | `@lavamoat/webpack@2.2.3` with generated package policies and reviewed overrides                             | Opt-in production webpack commands. Normal Rspack commands continue to use their existing configuration.                                                                                                                                       |
| Desktop renderer                                               | The same webpack policy integration, using an explicit `webpack.config.lavamoat.js` entry                    | Opt-in renderer build; this does not sandbox Electron main, preload, or native modules.                                                                                                                                                        |
| Mobile iOS/Android                                             | `@lavamoat/react-native-lockdown@1.0.0`, adapted to OneKey's Metro/common/segment pipeline                   | `ONEKEY_MOBILE_LOCKDOWN=true`; default disabled. Intrinsic hardening in both runtimes, without package compartments or package permission policies. See [mobile initialization and acceptance matrix](../apps/mobile/docs/mobile-lockdown.md). |
| Extension, web-embed, Electron main, CLI, build-system runtime | No LavaMoat package-policy integration in this change                                                        | Their policy directories remain placeholders. Existing platform SES controls are separate from LavaMoat package confinement.                                                                                                                   |

Web and Desktop renderer run application UI/background code in one JavaScript runtime. Each LavaMoat package compartment has its own global view while using that runtime's hardened intrinsics. Electron main/preload and process-owned native resources remain separate trust boundaries.

Mobile production `main` and `background` run in separate Hermes heaps in one native process. Each independently repairs and hardens its own intrinsics; neither runtime's readiness proves the other's. JavaScript state is per-runtime, while native storage and module singletons can be process-shared. Lockdown changes neither native ownership nor storage initialization order. Main/background bundles remain version-locked; native-versus-JavaScript compatibility still needs verification.

## Web and Desktop builds

Run commands from the repository root after a successful policy-compliant dependency installation:

```sh
# Generate both enabled policies, normalize them, and rebuild review reports.
yarn lavamoat:policy:all

# Build with the committed effective policies; does not regenerate them.
yarn lavamoat:build:web
yarn lavamoat:build:desktop-renderer

# Verify the final Web artifact with isolated Chromium profiles.
yarn exec playwright-core install chromium
yarn lavamoat:smoke:web
# Also verify the real health service instead of the controlled CI response.
yarn lavamoat:smoke:web --live-health-check

# Alternatively, generate or build one target.
yarn lavamoat:policy:web
yarn lavamoat:policy:desktop-renderer
yarn lavamoat:build:all
```

The commands set `ONEKEY_LAVAMOAT=1`; generation also sets `ONEKEY_LAVAMOAT_GENERATE_POLICY=1`. Protected build commands explicitly clear generation mode. Generation discovers requested permissions and does not prove enforcement or approve them. Both the tooling dependency and webpack's transitive `lavamoat-core` resolve to reviewed `18.0.5`; the resolution keeps policy generation and enforcement on the same version. Upgrades must pass dependency review and the release-age gate. It skips asset minification and source maps because policy analysis precedes those stages. Policy-only generation emits no deployable bundle, so the Web version manifest and service-worker plugins run only for normal and protected production builds. Adding the environment flag to a normal Rspack command does not turn Rspack into a LavaMoat build. Desktop's explicit [webpack entry](../apps/desktop/webpack.config.lavamoat.js) preserves that distinction.

[The integration helper](../development/webpack/lavamoat.js) places the runtime in one dedicated `lavamoat-runtime.<contenthash>.bundle.js` asset and prepends the untouched SES source after minification. The dedicated runtime remains independent of `splitChunks.maxSize`, which can rename and split application entry chunks. HTML loads it before application modules; source maps, the final content hash, and SRI cover the resulting asset. This avoids the upstream separate, relative, extensionless `./lockdown` script dependency. Enforcement builds fail if the final runtime is missing SES, contains transformed SES, or duplicates the prelude. The real webpack regression exercises split initial chunks and an asynchronous chunk, verifies SRI against final bytes, and rejects missing or duplicated preludes. Full application startup still requires the artifact smoke tests below.

After intrinsic repair and before hardening, a narrowly scoped static shim installs the shared [web intrinsic polyfills](../packages/shared/src/polyfills/webIntrinsics.js) and `Symbol.metadata` for Lit/AppKit. It is bundled with esbuild into `node_modules/.cache/lavamoat/`, not committed as a generated source file. The normal application bootstrap reuses the same intrinsic code and does not repeat mutations of frozen `Symbol.unscopables`. DOM, IndexedDB, timer polyfills, crypto, and the rest of application bootstrap are not included in this privileged shim. SES itself captures `Object.fromEntries` and `Array.prototype.flatMap` during loading; the later shim cannot make hosts without those baseline methods compatible.

The protected-only shim also binds the initial native `fetch` and `requestAnimationFrame` functions to the real host global. Core `18.0.5` does not convert the receiver for initial writable function endowments, so the existing shared Fetch interceptor otherwise fails before sending its health request. Only these two literal names are adapted, only when they are own writable data properties containing functions; their property flags are preserved. Missing, accessor, or non-writable properties remain untouched. The binding changes the initial function identity/name and fixes its receiver even for an explicit `.call(otherReceiver)`. It adds no policy grant and leaves the normal Rspack bootstrap and mobile Fetch interceptor unchanged. This is a compatibility adjustment for these two initial browser functions, not a general receiver repair; reassess it with the same tests when upgrading core.

A separate [core `18.0.5` security patch](../patches/lavamoat-core+18.0.5.patch) prevents read-only views of writable top-level functions from binding package replacements to the privileged root global. Without it, a package granted only `fetch: 'write'` could recover ungranted root properties through `this` when another package called its replacement. The patch restricts the existing parent binding to nested methods; top-level replacements retain the reader's compartment or explicit receiver and remain dynamically visible. The real-browser regression checks both implicit and explicit calls, proves that a captured receiver cannot reveal a synthetic host secret, DOM, or XMLHttpRequest, and preserves real HTTP/animation-frame delivery, property flags, denied capabilities, and compartment-local shadows that cannot change shared values. The initial-function shim and the receiver-confinement patch address different failure paths; neither expands the approved policy.

A [pinned webpack plugin patch](../patches/@lavamoat+webpack+2.2.3.patch) resolves package ownership from webpack's physical module resource while retaining the full loader request as the module identity. This supports Tamagui's virtual `matchResource` CSS requests without trusting the virtual filename as a package boundary. Policy generation uses the same safe exclusion check as enforcement: inline loader requests remain inspected and wrapped, including requests that attempt to inject the exclude loader. Webpack JavaScript modules produced from other file types use a JavaScript diagnostic filename so that the core inspector analyzes their loader output, including CSS font URL construction, instead of silently skipping it by source extension.

Generation and enforcement also prefer canonical names from the production dependency graph over names from development tools. The complete dependency map remains the fallback for bundled modules that are reachable only through development dependencies. This prevents macOS-only `dmg-license` from changing the shared `crc` and `buffer` compartment names compared with Linux. The initial migration renames 17 Web and 8 Desktop resource owners and their corresponding edges; it preserves their capabilities and requires no manual override migration. Their effective permissions remain unchanged.

LavaMoat blocks dependency assets emitted without an explicit loader. The [raw WASM loader](../development/webpack/lavamoat-wasm-loader.cjs) admits only the resolved `@onekeyfe/kaspa-wasm/kaspa_bg.wasm.bin` and `zbar.wasm/dist/zbar.wasm.bin` files, which their browser loaders fetch at runtime. It validates the real resource path again when invoked, preserves the binary bytes and hashed asset URLs, and does not exclude their JavaScript from compartment enforcement. Other dependency assets retain the upstream emission restriction.

The reviewed Web/Desktop overrides for `sonner@1.4.41` provide the DOM constructors used by its bundled DOMPurify 3.0.10 sanitizer. Static analysis misses the default-parameter alias through which this code reads its compartment global. The override grants seven constructors, four `NodeFilter` constants, and only `trustedTypes.createPolicy`/`getAttributeType`; it does not grant the entire `window`. [The execution regression](../development/lavamoat/webpack-host-globals.test.cjs) loads the shipped Sonner implementation, reproduces failure without the override, checks that sanitization stays enabled and removes malicious markup, and checks that direct `fetch`, `XMLHttpRequest`, `WebSocket`, and beacon access remain unavailable. The existing whole `document` grant still conveys DOM authority, including indirect network effects; this UI dependency is not an offline sandbox.

The React Native Web `Dimensions` override adds only `screen.height`, `screen.width`, and `devicePixelRatio`, which its `win = window` alias hides from static analysis. These values preserve live host getters. The same host-global regression exercises the shipped `Dimensions` code with initial dimensions, resize notifications, a changed pixel ratio, both document and `visualViewport` sizing, and listener removal. It rejects writes to the scalar getters and confirms that unreviewed `screen` properties remain unavailable.

The `worker-loader` inline runtime receives `Worker`, `Blob`, `URL.createObjectURL`, and `URL.revokeObjectURL` through a reviewed override. Its computed constructor lookup hides these reads from static analysis. The current caller is `@onekeyhq/kit`, which creates the blockie-avatar worker; the regression requires review when another package gains this edge. This is a **code-execution capability**: a caller can supply worker source, and the resulting child Worker has its own JavaScript heap and ambient browser capabilities, including networking. The child is outside this PR's SES/package-policy coverage. Inspection of the emitted `createAvatarList.worker.*.bundle.worker.js` confirms that it contains neither the LavaMoat runtime nor the SES prelude. The real Chromium fixture exchanges a message through the shipped loader, verifies object-URL revocation and the denied `SharedWorker` path, and confirms hardened parent intrinsics alongside the child's unfrozen intrinsics and available `fetch`. No request is made from the child. Switching to a separate emitted worker URL alone would not extend package confinement to that realm.

The `react-virtualized@9.22.6` resize detector similarly aliases `window`. Its `WindowScroller` caller omits the optional `hostWindow` argument, so both targets grant only `document.createElement`, `getComputedStyle`, `requestAnimationFrame`, and `cancelAnimationFrame` for supported modern hosts. The shipped detector is exercised in a real Chromium fixture: initialization fails without the override, listener registration and measured resizing work with it, pending animation frames can be cancelled, and listener removal stops callbacks. Direct network/storage globals, `document.cookie`/`defaultView`, and legacy event/frame APIs remain unavailable through the compartment global. These four method grants are not a DOM security boundary: returned elements expose their real `ownerDocument.defaultView`, and `AutoSizer` explicitly passes that raw host window. The fixture also records this broader DOM/network authority rather than treating syntactically narrow grants as confinement.

The resolved `@onekeyhq/core>near-api-js>node-fetch` browser adapter receives only `fetch`, `Headers`, `Request`, and `Response`. Its four emitted copies share the same policy identity and obtain these fields through `getGlobal()`. This override explicitly grants network authority; it does not expose the entire window. The real-browser regression loads the shipped adapter, reproduces the missing-permission failure, sends a local HTTP request, checks direct/default Fetch receiver behavior and constructor/response identity, and verifies that decorating the adapter export does not modify the host `fetch` function.

The `engine.io-client@6.5.3` ESM browser-global provider receives only `setTimeout`, `clearTimeout`, `WebSocket`, and the read-only `onpagehide` presence marker. Its consumers import the provider's compartment global, so granting these capabilities to the timer utility itself would not repair the missing reads. The shipped timer utility binds both cached native timers and current timers; the browser WebSocket constructor uses the same provider, and polling selects `pagehide` for teardown. The regression exercises both timer modes and cancellation, preserves modern page-hide detection, and completes a real local WebSocket handshake, message exchange, and close. This explicitly grants WebSocket network authority to the four reviewed consumers; it is not destination filtering. Direct fetch, storage, DOM, `XMLHttpRequest`, and legacy `MozWebSocket`/`ActiveXObject` access remain unavailable through this provider. Modern XHR remains governed by its own consumer policy.

Web alone grants `posthog-js@1.379.1` the host capabilities used by the existing OneKey analytics configuration; Desktop resolves its no-op adapter and receives no PostHog override. The override supplies native event methods, Fetch with cancellation, three session-storage methods, and specific live address, screen, viewport, and scroll fields. The existing local-storage methods and whole `document`/`navigator` already convey persistence, DOM, and network authority. **The whole native `history` object is an explicitly reviewed, high-risk mutable navigation capability**: the configured `capture_pageview: 'history_change'` patches real `pushState`/`replaceState`. Deep read grants would patch only a detached copy, and this LavaMoat version rejects deep write grants. The override therefore permits changes to host History methods and other history navigation. Deep Location grants also preserve native setters: even `location.href: true` permits navigation, as the fixture verifies with a same-document hash change. These are not read-only or destination confinement guarantees. The shipped-SDK regression retains the app's selector-limited autocapture, copied-text exclusion, text/attribute masking, localStorage+cookie persistence, and disabled recording/flags/surveys. With a synthetic key and a loopback endpoint it checks native history return values/state, real browser back/popstate, event listener removal, masked click payloads, and native Fetch delivery with unchanged batching/compression. Upstream `historyAutocapture.stop()` removes its popstate listener but retains method wrappers; the isolated test explicitly restores and verifies the original host methods. No recorder, survey, XHR fallback, Worker, or WebSocket capability is added for this modern-browser path.

## Policy review and trust boundaries

For each target, `policy.json` is generated and `policy-override.json` is the reviewed adjustment. Normalization only rewrites generated policies; reviewers must commit canonical formatting for manual overrides themselves. [Review reports](review/README.review.md) analyze their merged effective policy and separately list explicit denials. Regenerate reports after changing either input.

Reviewers should examine the source change and policy diff together:

1. Explain every new package edge and privilege increase. A generated `true` value records an observed request, not a security approval.
2. Review network, storage, DOM injection/navigation, dynamic execution, hardware access, crypto, desktop/extension bridges, and native/builtin authority. Check dependencies that can call a resource possessing those capabilities as well as the resource itself.
3. Treat whole-object grants such as `navigator: true` and `document: true` as broad authority. They include sensitive descendants even when `navigator.hid` or `document.cookie` is absent as a separate policy key. The reports intentionally classify these grants in multiple relevant categories.
4. Preserve the distinction between a narrow scalar such as `navigator.userAgent` and a whole object or a method returning a powerful object. Reports are a prioritization aid, not a proof that uncategorized globals are harmless.
5. For a deny override, test the affected real operation. Do not broaden permissions or exclude a package merely to make a build pass. Global aliases such as `window` and `globalThis` refer to the package compartment's global view; their names alone do not imply an unrestricted host global.

The loader-output inspection fix changes globals in six resources per target; resource counts, package edges, builtins, and other generated policy fields are unchanged. This comparison excludes the manual compatibility overrides described above; the effective-policy reports include both inputs. This snapshot records source attribution, not approval:

| ---------------- | --------- | ----------------------------- | ------------------------ |
| Web              | 4326      | 3297 → 3355                   | 64 / 6                   |
| Desktop renderer | 4279      | 3405 → 3511                   | 112 / 6                  |

The first-party additions include `URL` for [CSS font declarations](../packages/components/src/hocs/Provider/web-fonts.css), DOM/observer/timer usage, and 13 writable UI/developer fields per target. The [real webpack fixture](../development/lavamoat/webpack-loader-policy.test.cjs) verifies font URL generation and protected execution. [Web optional-chain lowering](../development/babelTools.js) explains why existing menu, storage, and extension checks produce broader `desktopApiProxy`, `localStorage`, and `chrome` requests than the corresponding Desktop paths. The only other changed globals are Expo's `__EXPO_ROUTER_HYDRATE__` read and css-loader's generated `module.id` references in shared and two external CSS resources. No new `fetch`, `XMLHttpRequest`, `WebSocket`, or Node builtin grant appears in this delta.

Desktop's components policy adds three [application-menu IPC calls](../packages/components/src/layouts/Navigation/Tab/TabBar/Menu.tsx). Of kit's 45 new `desktopApiProxy` paths, eight have direct callers outside DevSettings/Gallery: `appleAuth` and `oauthLocalServer` in [OAuth](../packages/kit/src/components/OneKeyAuth/OAuthPopup/OAuthPopup.desktop.tsx), `appUpdate.getPreviousUpdateBuildNumber` in [Bootstrap](../packages/kit/src/provider/Bootstrap.tsx), the two Bluetooth settings methods in [hardware setup](../packages/kit/src/views/Onboardingv2/pages/ConnectYourDevice.tsx), `security.setContentProtection` in [recovery-phrase protection](../packages/kit/src/hooks/useRecoveryPhraseProtected/useRecoveryPhraseProtected.desktop.tsx), `system.getMediaAccessStatus` in [QR scanning](../packages/kit/src/views/ScanQrCode/components/index.tsx), and `webview.getPreloadJsContent` in [DesktopWebView](../packages/kit/src/components/WebView/DesktopWebView.tsx).

The other 37 direct kit references are confined to [desktop API tests](../packages/kit/src/views/Setting/pages/Tab/DevSettingsSection/DesktopApiProxyTestDevSettings.tsx), [developer settings](../packages/kit/src/views/Setting/pages/Tab/DevSettingsSection/index.tsx), and [notification gallery](../packages/kit/src/views/Developer/pages/Gallery/Components/stories/NotificationGallery.tsx): seven storage read/write/clear paths, three biometric paths, four developer paths, four purchase paths, four notification paths, twelve system paths, and one each for test update feeds, native version lookup, and WebView cache clearing. These remain pending production-surface review. They are not proven unreachable in production: the [test route](../packages/kit/src/views/Setting/router/basicModalSettingRouter.ts) is registered unconditionally and its normal [settings entry](../packages/kit/src/views/Setting/pages/Tab/config.tsx) uses runtime `devSettings.enabled`. Kit already has whole-object `desktopApi: true`; denying only the new Proxy paths would not establish equivalent host isolation. Keep rollout opt-in until a coordinated review covers production developer routes, legacy bridge access, imported wrappers, and real denied-operation tests. No deny override was added merely to make this snapshot appear narrower.

The trusted computing base includes the application root, the bundler/plugin, SES, policy generation and overrides, the explicit static shim and its dependencies, excluded modules, and host endowments. Ordinary CSS and SES modules are excluded explicitly by the integration; Tamagui's inline virtual CSS requests remain wrapped. Any expansion of these exclusions or shims changes the security boundary and requires source review.

Package permissions limit access to ambient capabilities and other packages. They do not validate transaction intent, authenticate users, hide secrets deliberately passed to a dependency, or prevent misuse of an already granted capability. Mobile intrinsic hardening does not restrict ambient networking/native-module access. Installation approvals constrain which scripts may run, not what an approved script may do. Native code, Electron main/preload, and compromised build or release infrastructure require their existing defenses.

The Web/Desktop lockdown options preserve console/error diagnostics and locale behavior and use `overrideTaming: 'severe'` for existing library compatibility. These compatibility choices must not be represented as eliminating every side channel. Mobile uses its adapter's separate Hermes options and SES dependency tree; do not mix web SES into the mobile realm.

## Installation policy

The [installation guide](supply-chain/README.md) is authoritative for dependency changes and local migration. Yarn starts with `enableScripts: false`; exact reviewed package builds can be enabled through native Yarn metadata, backed by the committed [script approval inventory](supply-chain/install-scripts.json). The repository plugin validates configuration and Git sources, checks script execution, and audits the installed workspace graph before the `afterInstall` setup command.

```sh
yarn install --immutable
yarn lavamoat:supply-chain:inventory
yarn lavamoat:supply-chain:check
yarn lavamoat:git-dependencies:check
```

Inventory emits review candidates; it does not approve or edit them. A dependency source, checksum, or lifecycle-command change must be reviewed again. Unknown scripts remain blocked and make the installation audit fail. The Git checker also performs upstream provenance checks; running an offline inventory is not equivalent to that verification.

## Validation and CI

The host-global fixtures require a Chromium executable. Install Playwright Chromium with `yarn exec playwright-core install chromium` (Linux CI uses `--with-deps`), or set `ONEKEY_LAVAMOAT_TEST_CHROME` to an existing executable. The fixture also detects the standard macOS Google Chrome installation. It launches its own temporary profile and never attaches to an existing browser; a missing browser fails the test. The Web artifact smoke accepts the separate `--chrome` option.

```sh
# Tooling, effective-policy reports, and actual webpack/runtime fixtures.
yarn lavamoat:test-tooling
yarn lavamoat:validate-artifacts
node --test development/lavamoat/webpack-loader-policy.test.cjs

# Clean-worktree policy freshness and both protected builds.
yarn lavamoat:ci:all

# Installation policy fixtures.
yarn lavamoat:supply-chain:test

# Mobile adapter and compiler fixtures; native execution remains separate.
yarn jest --runInBand --runTestsByPath apps/mobile/plugins/__tests__/mobileLockdown.test.js --coverage=false
ONEKEY_MOBILE_LOCKDOWN=true NODE_ENV=production node apps/mobile/scripts/check-mobile-lockdown.js
ONEKEY_MOBILE_LOCKDOWN=false NODE_ENV=production node apps/mobile/scripts/check-mobile-lockdown.js

# Repository commit and PR readiness gates.
yarn agent:check --profile commit
yarn agent:check --profile pr
```

The policy freshness workflow regenerates policy/review artifacts, rejects changes outside the two generated webpack policies and review reports, checks the diff, and builds both protected webpack targets. Installation approvals and manual overrides are outside this generated scope. Run the scope/freshness checks from a clean checkout so unrelated local edits are not mistaken for generated changes. Repository CI remains read-only for validation. After building, the Web smoke command launches fresh Chromium profiles for the root and a deep link, checks rendered controls and content, frozen intrinsics, a rejected prototype mutation, Promise/timer delivery, uncaught exceptions, and local asset failures. It also requires the application health request to reach Chromium and return HTTP 200, followed by removal of any offline indicator. This catches receiver failures whose caught console errors are removed by production minification. By default only `/wallet/v1/health` receives a controlled successful response at the browser network boundary; other requests remain unchanged. The `--live-health-check` option disables that fixture to verify the actual health service. The report distinguishes fixture and live responses and records the index hash, runtime evidence, and screenshots in a temporary directory; CI uploads those artifacts. An existing browser executable can be selected with `--chrome`, and `--output` selects an evidence directory. The smoke uses no existing wallet profile and does not exercise signing.

The `@onekeybot update-policies` workflow is limited to authorized repository participants and same-repository PRs. It consumes validation patches, verifies the PR head, restricts changes to generated policies/reports with regular file modes, and creates a commit using a temporary Git index. It cannot update installation approvals, manual overrides, or executable files. It does not check out or execute PR code with its write token. Bot-generated updates still require policy review; a default `GITHUB_TOKEN` push may require a manual CI rerun.

## Rollout and rollback

| Layer                        | Rollout condition                                                                                                                                                                                                           | Rollback                                                                                                                                                                                                                               |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Web/Desktop package policies | Review permissions, pass generation/build/runtime fixtures, then verify the protected production artifacts in browser/Electron on representative wallet flows. Keep the explicit build opt-in until acceptance is recorded. | Build and distribute the normal target artifact, then reload/restart the JavaScript runtime. Reverting a policy alone is not equivalent to disabling enforcement. Existing platform SES hardening may still apply.                     |
| Mobile lockdown              | Keep disabled by default until the [native acceptance matrix](../apps/mobile/docs/mobile-lockdown.md#native-acceptance-matrix) is complete for both main and background.                                                    | Set `ONEKEY_MOBILE_LOCKDOWN=false`, rebuild matching common/vendor/entry artifacts, distribute the compatible build, and restart both runtimes. Already hardened intrinsics cannot be unfrozen.                                        |
| Installation gate            | Review the installed dependency inventory and approvals independently of runtime rollout.                                                                                                                                   | Revert the coordinated policy, Yarn configuration, and plugin changes through source control if necessary. There is no supported bypass environment switch; never use a runtime rollback as a reason to enable every lifecycle script. |

Android native execution, native Release union/segment loading, production OTA rollback, startup timing and heap effects, unlock, test-key signing, background hardware-wallet transport, and WalletConnect remain pending. Node VM checks and bytecode compilation do not establish those remaining device results.

For Web/Desktop, attach evidence from the exact protected artifacts: deep-link startup, SES presence, denied-capability behavior, frozen intrinsics, unlock/signing with test credentials, hardware/bridge calls, and lazy WalletConnect/Lit loading. Successful compilation and the small runtime fixture do not replace full application acceptance.
