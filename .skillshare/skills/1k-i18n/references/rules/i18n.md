# i18n command reference

Use `<dir>` for `.tmp/i18n/<task>/`. Remote commands reach OneKeyHQ/onekey-i18n through the
GitHub API (`gh auth login` or `ONEKEY_I18N_TOKEN`); no checkout or credential wrapper is needed.
The required sequence, mode rules and confirmation boundary are in `SKILL.md`.

## Fill a draft

```bash
yarn i18n:workflow inspect --file <dir>/draft.json
yarn i18n:workflow fill --file <dir>/draft.json --translations <dir>/patch.json
```

A patch identifies candidates by their existing `id`; `key` supplies the proposed
name. Without `id`, `key` must uniquely identify an existing draft entry.

```json
{
  "entries": [
    {
      "id": "candidate-id",
      "key": "travel_mode__title",
      "action": "upsert",
      "translations": { "en_US": "Travel Mode", "zh_CN": "旅行模式" }
    },
    {
      "id": "reuse-candidate-id",
      "reuse": "global.not_now",
      "action": "upsert"
    },
    {
      "id": "technical-string-id",
      "action": "ignore",
      "reason": "Internal diagnostic text; not user-facing."
    }
  ]
}
```

The translation example is abbreviated: complete every draft locale before preview.
`reuse` copies all locale values; explicit translations override named values only.
For updates, preserve unaffected languages and regenerate those affected by a change
in meaning. Reuse depends on context, not English text alone.

Inspect unresolved expressions in source before setting `"unresolvedReviewed": true`
through `fill`. Add required dynamic copy with its source location to the draft;
add scan paths for imported copy rather than treating scanner output as complete.

For larger batches, `table.columns` avoids repeating locale names. Use IDs from
this exact draft, in the order given by `table.ids`; each ID needs a decision in
`entries`. Do not also put that row's translations in `entries`.

```json
{
  "entries": [
    { "id": "candidate-id", "key": "travel_mode__title", "action": "upsert" }
  ],
  "table": {
    "ids": ["candidate-id"],
    "columns": { "en_US": ["Travel Mode"], "zh_CN": ["旅行模式"] }
  }
}
```

Include every required locale column; this example abbreviates the language set.

## Single-key commands

After the initial sync, the positional command creates a draft without writing anything:

```bash
yarn i18n:add transaction_failed__msg "Transaction failed." "交易失败。" --sync <dir>/sync.json --out <dir>/draft.json
```

Fill remaining languages and follow the normal preview/confirmation/apply workflow.
It defaults to `complete`; use `--mode update` for intended wording updates.
A ready locale-to-text JSON can directly produce the preview:

```bash
yarn i18n:add transaction_failed__msg --mode update --sync <dir>/sync.json --translations <dir>/all-locales.json --project-name "Monorepo v5" --out <dir>/plan.json
yarn i18n:add --apply <dir>/plan.json --approve <confirmed-hash>
```

Apply opens the onekey-i18n PR and pulls its CI preview, as in the main workflow. Use `yarn i18n:workflow --help` or
`node development/scripts/i18n/i18n-add.js --help` for other options.

## Old-key cleanup

After a confirmed key migration succeeds, offer cleanup separately. Use only old
keys from its recorded mapping that still exist in onekey-i18n; exclude replacement keys
and shared keys still in use. `i18n:unused` scans current source, not released versions.
Released bundles retain their translations; check remaining source/dynamic usages
to protect future builds.

1. Establish a fresh sync and retain its generated-file backup. After an apply, use
   `sync --verify-current` as described in recovery when no current sync exists.
2. Save the exact old-key names as a non-empty JSON array in `<dir>/old-keys.json`.
   Prepare a dry run, inspect warnings and skipped files, and verify replacement
   translations in every locale before asking the user to approve the deletion list:

   ```bash
   yarn i18n:unused --include-tests --delete-central --delete-keys-file <dir>/old-keys.json --project-name "Monorepo v5" --format json --output <dir>/delete-preview.json
   ```

3. Once that list is approved, repeat the command with `--yes` and a new output
   filename; it removes the keys through a new onekey-i18n PR (add `--pull-after-delete`
   to pull its CI preview). Do not replace the exact list with `--delete-limit` or a global cleanup.
   A declined or unanswered request leaves old keys intact.
4. Pull using `sync --sync <pre-delete-sync.json>` and a new output path. Verify that
   only the approved old keys disappeared across all locales and the generated enum,
   replacements/shared keys remain intact, and report any unrelated changes.
   Rescan the migrated module and run appropriate checks; keep the deletion receipt
   and backup. Never manually remove entries from generated files. Then open the
   onekey-i18n PR reviewed and, after it merges, pin its release with `yarn i18n:pull`.

## Recovery

- **Baseline/source/onekey-i18n changes:** preserve translation decisions, refresh and
  rescan, then generate a new plan for confirmation. To refresh an unchanged prior
  pull without committing or discarding its generated output:

  ```bash
  yarn i18n:workflow sync --sync <dir>/sync.json --project-name "Monorepo v5" --out <dir>/sync-next.json
  ```

  Scan against `sync-next.json`, then reapply reviewed decisions. Do not attach a
  new baseline to an old translated draft to conceal remote changes.

- **Unknown generated edits or failed pull:** preserve and inspect them; do not
  discard edits or bypass guards. For a reviewed pull repair, run
  `yarn i18n:pull` (latest release), `--version <YYYY.MM.DD.n>` or `--pr <number> --wait`,
  then verify the original plan.
  If the previous apply has no current sync record, use `sync --verify-current
--project-name "Monorepo v5" --out <dir>/sync-next.json`. It pulls into a temporary
  directory and accepts a new baseline only if every generated file matches the
  workspace byte for byte. A mismatch preserves current files and stops for review.
- **Interrupted apply:** keep the plan and receipt; rerun `apply` with the same
  confirmed hash. Let the script reconcile completed operations. Report conflicts
  instead of blindly retrying writes or rolling back others' translations.
- **Project/language mismatch:** verify the intended project. For an intentional
  language-code mapping, pass `sync --locale-map <map.json>` (for example
  `{"en_US":"en"}`). Do not omit a locale, merge two locales into one stored record,
  or add project languages without authorization.
- **Stale lock:** inspect `plan.json.lock` and its process; remove only a confirmed
  stale lock for this plan.

```bash
yarn i18n:workflow verify --file <dir>/plan.json
```

Inspect the receipt and full locale diff, including unrelated translations imported
by the pull. Do not manually prune generated hunks to hide those updates. Initial
pull and pre-write checks do not lock onekey-i18n; apply refuses to commit when its main
changed the same files after the release it read, but do not describe apply as atomic.

## Lock file

`packages/shared/src/locale/i18n.lock.json` records where the generated files came
from (`release` tag, or the onekey-i18n `pr` and commit of a CI preview) and their digest.
`yarn i18n:check-lock` fails on hand edits, on extra locale files and on files from an unmerged
PR preview; `node development/scripts/i18n/i18n-pull.js --verify --allow-preview`
accepts a preview while the onekey-i18n PR is open.

For script changes, run `yarn i18n:test`. For code wiring, follow repository checks.
