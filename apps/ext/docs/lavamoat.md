# Protected extension webpack build

The default production `build:v3` and `build:all:v3` commands use the protected webpack pipeline with the production MV3 manifest and its existing `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'` CSP. It does not enable eval, inline scripts, or Playwright's CSP bypass. The explicit `build:v3:unprotected` and `build:all:v3:unprotected` commands retain the previous complete Rspack rollback pipeline. Both builds use the same production resolver, including native component mocks, Sentry compatibility, and the single ESM algosdk entry.

| Compiler / policy                | Entry points                                                                           | Runtime placement                                                                              |
| -------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `webpack/ext/mv3/pages`          | Popup, expanded tab, side panel, standalone window, content iframe, passkey, offscreen | One packaged `lavamoat-runtime.<hash>.bundle.js` referenced by each HTML page before its entry |
| `webpack/ext/mv3/background`     | MV3 background service worker                                                          | SES and the module runtime inside `background.bundle.js`; no split or asynchronous chunks      |
| `webpack/ext/mv3/content-script` | Isolated-world content script in each matching frame                                   | SES and the module runtime inside `content-script.bundle.js`; no split or asynchronous chunks  |

Each page, service worker, and content-script frame has its own JavaScript realm and independently initializes SES. Browser-managed extension storage and messaging are shared resources, while JavaScript objects and globals are local to each realm. The pages policy is the union of the three page entry graphs, not a separate least-privilege policy for every HTML page. Every compiler validates exactly one intact SES source and one LavaMoat runtime before emitting an enforcement build.

`injected.js` is the existing copied provider bundle that runs in the site's MAIN world. It and the two trusted page bootstrap copies (`preload-html-head.js` and `ui-popup-boot.js`) remain byte-identical to their inputs and still pass through the final remote-code checks. The build does not apply SES to the DApp's globals or prototypes. The provider's internal packages are outside these three policies. Isolating that provider requires a separate architecture; isolation of the content-script realm does not isolate MAIN-world code.

The supported production extension pipeline is Chromium MV3 (Chrome and Edge). The repository's release workflow invokes `build:all:v3` and packages `chrome_v3`; the remaining Firefox/MV2 manifests are not an active production build target in this pipeline.

The extension polyfill entry points use the existing `globalShim` to install missing `global`/`globalThis` aliases without changing intrinsics. Importing the old `core-js/es7/global` after SES would unconditionally redefine the frozen `Function.prototype.toString`; removing that redundant shim reduces the content-script policy from 73 to 46 resources and removes the `__e`/`__g` writes. Ordinary and already-locked fresh realms are covered by the same alias regression.

The extension manifest declares all six imported OneKey workspaces (`components`, `core`, `kit`, `kit-bg`, `qr-wallet-sdk`, and `shared`) so policy generation and enforcement use package ownership instead of first-party file-level external identities. The explicit overrides reuse the reviewed shipped browser adapters: `node-fetch` gets its four fetch-related aliases in pages/background; the Engine.IO global provider gets its four timer/WebSocket/page-hide aliases only in background; pages additionally get the existing React Native Web dimensions, resize detector, and Sonner sanitizer aliases. PostHog resolves to the extension no-op implementation, and workers are packaged files, so neither Web PostHog nor inline-worker Blob permissions are carried into the extension. Content-script overrides grant nothing. Generated first-party permissions remain a review surface; these compatibility overrides are not a claim of complete least privilege.

The packaged Worker factory uses a literal extension-root URL. Upstream `worker-loader` otherwise reads Webpack's public path through `require.p`, which LavaMoat intentionally omits from the module runtime. The extension adapter accepts only the exact default Worker factory and this compiler's content-hashed filename; a changed constructor, options, or source shape fails compilation for review. The actual MV3 fixture exchanges messages from popup, passkey, and offscreen pages under the unchanged CSP. The child Worker still has its own unprotected heap: using a packaged URL does not install SES or package policies inside it.

Extension artifacts use the upstream numeric resource IDs, while generated and reviewed policy files retain canonical package names. The real MV3 permission regression runs in that production mode. Compression follows the normal extension's two passes, or three for the unsplit background, with one minifier worker. That worker has a separate V8 heap in the same operating-system process and handles one asset at a time; it does not share the compiler's retained graph heap.

Pages retain the shipping extension's 40-request asynchronous chunk limit and shared cache groups, with a 20,000-byte sharing threshold for the separate package modules. Webpack's `removeAvailableModules` removes a child definition only when that module is available through every parent path; it does not concatenate modules or change package ownership. A real two-entry browser regression checks independent page startup, nested lazy loading, retained definitions required by only one entry, exact dependency denial, unavailable ambient globals, unchanged SES bytes, and SRI. This establishes compatibility for eligible duplicate removal; the actual application must still pass the unchanged output size and chunk-count budgets.

The page compiler also extracts a shared SVG runtime used by popup and passkey icon imports. Only popup has those dependencies initially; passkey's asynchronous imports also need their definitions. The narrow cache group requires at least two users and preserves every module's package owner. A natural two-entry regression verifies the extraction, real asynchronous icon loading, separate per-page module caches, denied capabilities and final SRI. Sharing the packaged script does not share JavaScript heaps between pages.

Extension minification emits ASCII escapes for Unicode noncharacters such as U+FFFE. Their JavaScript string values are preserved, while Chromium can load the resulting extension scripts. Terser intentionally preserves tagged-template raw text even with `ascii_only`, so this option does not eliminate every possible noncharacter; loading the final artifact in Chromium remains an acceptance gate. The SES source is still inserted unchanged and checked by the runtime validator.

The protected page and background compilers replace the fixed imports in the physical `shared/src/locale/localeLoaders.ts` with reads of packaged JSON data. All 19 languages and the English alias keep the existing asynchronous API and failed-load retry behavior. The verified filename cache retains JSON module identity across aliases and upper-level promise-cache resets, avoiding repeated fetches and parsing. Compilation checks the loader's AST structure and complete language inventory, emits unchanged JSON bytes under content-hashed paths, and embeds the SHA-256 and byte length in the shared module. Runtime reads are restricted to those paths in this extension, reject redirects and failed responses, verify length and SHA-256 before parsing, and never merge JSON properties into another object. Both compilers emit identical files, which finalization deduplicates without sharing JavaScript heaps or parsed objects between realms. The normal Rspack pipeline and content scripts retain their original loading paths. No permission, CSP, or web-accessible-resource entry is added; the real MV3 regression also confirms a content script on a website cannot fetch these private extension resources. JSON data remains included in the existing total artifact budget.

## Commands

From the repository root:

```sh
yarn workspace @onekeyhq/ext lavamoat:policy
# Review all three generated policies and explicit overrides before enforcement.
yarn workspace @onekeyhq/ext build:lavamoat
```

`build:v3` finalizes and checks the protected output in the existing release directory, `apps/ext/build/chrome_v3`; `build:all:v3` then runs the unchanged zip pipeline. That script writes the official archive before modifying the working directory's name, version, and images for the development archive. Production smoke tests must use the official archive extracted to a fresh directory or an exact snapshot taken before that modification. The explicit `build:lavamoat` command keeps its separate output directory.

The per-compiler commands are `lavamoat:policy:pages`, `lavamoat:policy:background`, `lavamoat:policy:content-script`, and the corresponding `build:lavamoat:<compiler>` commands. `lavamoat:finalize` combines all three completed compilers into `apps/ext/build/lavamoat/chrome_v3` and runs the existing output checks, including CSP, packaged assets, remote code, source maps, and size budgets. Missing compilers or conflicting assets fail before replacing the previous final output. Policy generation is an audit operation and does not produce deployable application bundles.

## Verification and remaining acceptance

`development/lavamoat/webpack-extension.test.cjs` compiles real MV3 fixtures through the same three configurations and launches an isolated Playwright Chromium profile with the production manifest and CSP. It verifies popup/passkey/offscreen startup, background messaging, isolated content-script startup, a native DApp → content script → Chrome port → background → DApp round trip through the shipped bridge, rejection of iframe and missing-source messages, allowed `chrome.runtime` calls, denied undeclared dependency access and ambient globals, no-eval, frozen extension intrinsics, and unchanged MAIN-world intrinsics. It also checks that finalization rejects incomplete/conflicting compiler output and preserves the normal Rspack artifacts. Install the pinned browser with `yarn exec playwright-core install chromium`. The fixture uses the default Playwright browser cache, honors `PLAYWRIGHT_BROWSERS_PATH`, and accepts an explicit Chromium executable through `ONEKEY_LAVAMOAT_TEST_CHROME`; it does not depend on a machine-specific installation path. Branded Chrome and Edge no longer support the command-line extension-loading switches needed by this test.

`yarn workspace @onekeyhq/ext test:lavamoat --output <report-directory>` tests the finalized isolated output; add `--production-output` to test `build/chrome_v3` before `zip.js` modifies it. The harness first runs the unchanged artifact checker, rejects relaxed budget overrides, verifies all three protected runtimes and final HTML SRI, and snapshots the checked bytes. A dedicated disposable Chromium profile uses a private CDP pipe to pause new workers before installing native rejection observation and loading the extension. Pages are observed while blank before navigation; the application must create its actual offscreen document. It checks popup and expanded-page content, passkey's committed idle bootstrap (not WebAuthn authentication), runtime checks, and readonly empty-wallet DApp requests through the real background. Packaged resource, CSP, JavaScript, and native unhandled-rejection failures fail the run. Reports include artifact hashes and screenshots; no existing profile is read. The separate `smoke-lavamoat.test.cjs` regression proves immediate background, offscreen, and page rejections remain observable when SES defers its own reporting. A failed or over-budget candidate cannot enter this formal smoke.

The manually reviewed policy denies the top-level `chrome` capability for React Virtualized/Lightweight Charts browser detection and the two hardware SDK environment detectors. They receive only `chrome.runtime.id`; the SDKs also receive `chrome.runtime.onConnect.hasListeners` so their existing presence check still selects the extension environment. The MV3 fixture extracts both shipped SDK checks, runs the actual virtualized-size check and the chart condition, and proves storage, tabs, runtime connect, and listener registration remain unavailable even when a separately authorized writer replaces `chrome`. The `webextension-polyfill` adapter still intentionally receives the full Chrome/browser API to implement its proxy; it remains a privileged part of the trusted integration boundary.

The shipped bridge retains its original `event.source === window` check. LavaMoat's official `repairs/messageevent.js` maps same-window sources to the receiving compartment; the real browser regression verifies this behavior without granting the whole host window or changing the SDK.

To test an exact production content-script bundle, set `ONEKEY_LAVAMOAT_TEST_CONTENT_SCRIPT` to its path when running the same test file. This adds an application-content test with a clearly identified echo background, preserving the production manifest and CSP. It proves that content artifact's installation, startup, and bridge behavior; it does not prove the real wallet background or page UI.

The fixtures establish the runtime and permission boundary. Full generated-policy review, production build/output validation, and cold startup of the actual OneKey extension are separate acceptance checks; a passing synthetic fixture does not replace those checks. Existing extension E2E suites that set `E2E_MODE=true` or bypass CSP do not establish protected startup.
